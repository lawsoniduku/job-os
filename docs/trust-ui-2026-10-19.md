# Eligibility confidence and availability are separate

## User-visible behavior

Copilot and Briefing now label eligibility confidence **High**, **Good**, or **Unconfirmed**. The persisted verdict keys (`eligible` / `conditional`) remain compatible with saved applications. Explicit negative verdicts remain **Not eligible** and the existing search exclusions still apply.

Every result shows a reason beside its confidence label. Unconfirmed results always include an inline “Why unconfirmed” explanation, including old or incomplete thread snapshots. Availability has its own **Verified**, **Unverified**, or **Closed** label and reason. One label cannot supply evidence for the other.

When the deterministic engine's final reason actually cites a model inference, the card repeats the quoted evidence and displays the recorded model and check timestamp. Legacy records explicitly say when those metadata were not recorded. An unused stored inference is not presented as the basis of a deterministic decision. Posting text and model metadata render as escaped React text.

## Exact availability proof

The shared policy in `shared/jobTrust.js` is used by the API ordering, the merge of Briefing searches, and both result-card views. Verified requires all of:

- Current observation `status: ok`, proof version at least 4, provider `employer` or `jobboard` (including retained MyJobMag).
- `identity: exact`, a recorded HTTPS `evidence_url` matching this job's apply URL, a safe HTTPS `checked_url`, and a recorded 2xx HTTP response. URL fragments are ignored; query parameters remain part of identity. The checked URL may be the corresponding ATS API endpoint.
- A check within seven days, not in the future, and no source content change newer than the check.

An unknown/pending observation remains Unverified even when it retains a last-known open record. Retained conclusive closure is Closed until a newer conclusive open observation supersedes it. Old version 3 open checks are retained by the verifier for restrictions and retry context, but cannot earn this new auditable positive label. Deploy the availability workstream before expecting new Verified labels, then run its scheduled checker/backfill using the supplied runbook.

## Ordering

The highest group has both supported eligibility and verified availability. Next are jobs with positive evidence on one of those axes, followed by jobs with neither. Publication recency, then score and stable ID, order each group. This preserves uncertainty without hiding roles merely because availability could not be checked. Briefing uses the same ordering when combining independent role searches.

Role matching, deterministic country exclusions, expired deadlines, prior-year exclusions, and the existing discovery-age requirements remain gates before ranking. Trust does not revive an old or ineligible posting. Import timestamps never substitute for publication dates.

## Offline validation and honest measurement

User-supplied production baseline on October 19: 111 AI verdicts across 31,126 rows; availability unknown approximately 90.9% iCIMS, 90.1% Recruitee, 82.2% Phenom, and 100% Y Combinator. These are supplied baseline figures, not new measurements. No production service was queried for this change. Production after values remain pending the user-run trust report and backfill.

| Offline case | Previous behavior | Updated behavior |
| --- | --- | --- |
| Missing eligibility reason | Could show an Unconfirmed badge with no inline explanation | Visible fallback “Why unconfirmed” on every result |
| Eligibility High, no availability proof | Single eligibility badge and generic unavailable text | High and Unverified shown independently |
| Unconfirmed eligibility, exact current availability proof | Availability could be mistaken for eligibility | Unconfirmed and Verified shown independently |
| Latest unknown with retained open proof | Raw status and retained context could be confused | Unverified |
| Old/identity-less positive check | Raw `ok` could appear confirmed | Unverified until auditable proof exists |
| Model verdict | Reason could contain a quote but metadata was invisible | Quoted evidence, recorded model and timestamp; missing metadata stated |
| New uncertain row versus older fully evidenced current row | Publication date always led | Fully evidenced row leads; freshness gates still exclude old postings |
| Briefing combines role searches | Always re-sorted by newest | Preserves the same trust ordering as search |

Adversarial coverage includes missing/contradictory eligibility, evidence URL mismatches, query identity changes, unsafe URLs, missing proof fields, 403/404 response codes, stale/future timestamps, source changes, last-known records, escaped model text, trust ordering, and excluded/closed/prior-year gates.
